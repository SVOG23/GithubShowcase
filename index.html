Vouchlist

Trusted local recommendations from the people you actually know.

Live on iOS & Android ALPHABYTE
vouchlist.app 🔒 Private repository

Vouchlist replaces the anonymous five-star review with a vouch from someone in your circle. You find a plumber, a restaurant or a trip destination because a real person you're connected to stood behind it. The app covers three domains — Home Services, Food & Drinks, and Travel — each with its own capture flow and detail schema, all sharing one social graph. I designed, built and shipped it end to end, through Apple and Google review.

Engineering highlights

  • Privacy-preserving friend discovery. Contacts are matched by SHA-256 phone hashes with a shared salt — the server never stores a readable phone book, but the graph still resolves the moment a hash matches a profile.
  • Phone-OTP auth via Twilio Verify layered onto Supabase Auth, with a multi-step onboarding gate (profile → location → contacts → first vouch → circle) whose routing decision is a pure, unit-tested selector rather than a tangle of effects.
  • ~20 Postgres tables, row-level security on every one. Circles, memberships, invite codes, contact-graph entries, per-domain detail tables and block lists — visibility is enforced in the database, not by the client.
  • 26 screens on 10 React Context providers + TanStack Query, each provider a [Provider, useHook] tuple with optimistic writes and explicit invalidation.
  • Deno edge functions with an auditable trust boundary. Every function's verify_jwt is declared in config, so the public/private boundary shows up in a diff; the public weekly-digest job is bounded by an atomic once-per-6-days gate and reads no request input.
  • Invite deep links over universal links plus a custom scheme, with a static web fallback page for people who don't have the app yet.
  • CI/CD through EAS Build and EAS Submit, with Sentry crash reporting and PostHog analytics wired into the release build.

ModelMarketplace

A two-sided marketplace for trained ML models — buy it, or win it at auction.

iStartup Lab Micro-Grant, 2026 ALPHABYTE
🔒 Private repository

ML practitioners list trained models; buyers acquire them outright or win them at auction. Underneath the product it's an end-to-end exercise in building a real payments system on Stripe with strong server-side guarantees — multi-flow checkout, webhook reconciliation, row-level security and business rules enforced by the database. The University of Washington awarded it an iStartup Lab Micro-Grant for market viability and architectural rigor.

Engineering highlights

  • One webhook, three flows. Purchase, auction settlement and tier subscription all land in a single handler and dispatch on a transaction_type metadata tag — set on both the Checkout Session and subscription_data, because the subscription lifecycle events only ever see the latter.
  • Atomic, idempotent fulfillment. The transaction insert, model claim, ownership transfer, ledger append and seller-stat update all run inside one Postgres function keyed on a unique stripe_session_id. Stripe retries heal partial failures; duplicate events can't double-fulfill.
  • Anti-abuse lives in the database, not the UI. Postgres triggers enforce per-tier listing quotas (3 / 25 / unlimited), a one-hour re-list cooldown, and a unique partial index blocking duplicate active titles. The API translates the resulting error codes into human messages — the client-side check is only a hint.
  • Re-listing flips ownership instead of duplicating rows, so download counts, reviews and transaction history stay attached to one model identity across resales — which required an RLS policy that permits the write from the current seller or the current owner.
  • Stripe Connect onboarding is a database guarantee — the schema refuses inserts from sellers without a connected account, so a bypassed UI check changes nothing.
  • No hardcoded Price IDs. One-time and auction charges build price_data inline; subscriptions reuse a Price per (tier, interval, amount) via a Stripe lookup_key, so abandoned checkouts don't litter the account with objects.
  • Three Supabase clients, chosen deliberately — browser (RLS under the caller), cookie-aware SSR, and service-role for webhooks — kept in separate files because mixing them silently breaks either auth or RLS.

unrot

A linter for the config files that steer your AI coding agents.

Open source · MIT Published on npm
github.com/unrot-dev/unrot npm i -D unrot

Agent configs rot. The repo moves on — files get renamed, scripts get replaced, conventions change — while CLAUDE.md, AGENTS.md and .cursorrules quietly keep describing a codebase that no longer exists. Nothing checks them. unrot does: pure static analysis plus git history, no network calls, no telemetry, no LLM calls, and it never modifies your files. npx unrot check works at the root of any repo with zero configuration.

Engineering highlights

  • Seven rules with real teeth — broken references (with “did you mean…” recovery when a file has moved), oversized instruction files past where models stop following rules, cross-file contradictions, staleness measured against commit volume, eager @-imports, personal paths committed to shared configs, and repos with no agent config at all.
  • Deliberately conservative heuristics. Broken-refs forgives monorepo-relative paths, build artifacts, gitignored-but-present files, placeholders, package specifiers, script families and hedged “if it exists” phrasing — the goal is that every reported error is worth fixing.
  • Measured, not asserted. Precision was verified by hand on a 20-repo held-out corpus spanning Java, PHP, C#, Ruby, Go, C++ and Swift — ecosystems the rules were never tuned on — where 15 of 16 error-level findings held up. A mutation harness measures recall: 354 of 356 injected defects caught, with 440 of 440 negative controls staying quiet.
  • Found real rot in the wild across 69 popular open-source repos — dead source references in Microsoft's VS Code Copilot config, a nonexistent path in OpenAI's Codex AGENTS.md, and a committed instruction pointing at one maintainer's laptop.
  • Fleet mode scans an entire GitHub org — or a list, or a directory of clones — concurrently, and grades each repo A–D in one combined health report. Strictly read-only: it never opens PRs.
  • Built to be a CI gate — stable versioned JSON schema, meaningful exit codes, and a copy-paste GitHub Actions job.

Clipr.AI

Scan your hair, preview the cut, get the spec, then cut it yourself.

In development Computer vision
🔒 Private repository

A six-stage pipeline — Scan → Understand → Preview → Specify → Cut → Verify. You capture your hair from five guided angles, an AI analysis describes your current cut, you pick a target (catalog preset or reference photo) and preview it on yourself, then receive a precise Barber Card and a step-by-step Cut Coach. Rescan afterwards and the app compares the real result against the target. The long game is a consented dataset mapping current hair → target spec → actual result.

Engineering highlights

  • One spec as the source of truth. HaircutSpec v1 is a versioned schema shared by preview generation, the Barber Card, the Cut Coach and any future model — so the four surfaces can never drift into describing different haircuts.
  • Every AI capability sits behind a provider interface — segmentation, pose, hair analysis and preview generation — each with a working mock. Real providers (a vision LLM for analysis, FLUX.2 for previews, MediaPipe for segmentation and face landmarks) activate purely through environment variables.
  • Mocks that fail closed. Hair analysis refuses to emit a canned result, and once a real inference URL is configured nothing silently falls back to a mock — a dead service fails loudly instead of quietly serving fiction.
  • Photos of your face are treated as such. The mobile client holds only an anon key, storage is a private bucket with per-user folder policies, RLS covers every table, and captures are downscaled on-device before they ever leave the phone.
  • Security tested as data, not vibes — an RLS suite driven through PostgREST, a full end-to-end data-journey test, and a SQL suite run inside the database with ON_ERROR_STOP so a missing privilege fails the run instead of skipping it.
  • Honest scope. The README ships a limitations table — no AR measurement, per-view rather than joint multi-view generation, prompt-driven cross-view consistency — because overstating what a model does is how demos become liabilities.

Kivo

Play anywhere — peer-to-peer sports equipment rental, billed by the minute.

MVP complete Marketplace · Payments
🔒 Private repository

Find gear near you on a map, rent it by the hour, verify pickup with a code, play, verify the return, and pay for the minutes you actually used. One account both rents and lends. What makes it a marketplace rather than a form is that none of the money is decided on the phone — the client is trusted with a listing ID and a time window, and nothing else.

Engineering highlights

  • Price, commission and the clock all come from the server. Rental start and end are stamped by the database when each PIN verifies; the final charge is recomputed in SQL at return and captured through Stripe. The platform fee lives in a schema the client cannot reach.
  • Double booking is a constraint, not a code path — a GiST exclusion constraint over listing and time range makes two overlapping live bookings impossible whatever the app does.
  • A two-sided PIN handshake. The lender shows a pickup PIN the renter enters; the renter shows a return PIN the lender enters — so neither party can move the rental clock alone. The PINs live in a table with RLS on, zero policies and zero grants, unreachable through the API under any role; the only way in is a function that checks who's asking, what state the rental is in, and enforces attempt limits and lockout.
  • Home addresses stay hidden. Exact pickup locations live in their own table visible only to the owner and a renter with a live booking; the public listing carries a deterministically jittered point (120–250 m, seeded from the listing ID) so it can't be averaged away by repeated polling.
  • Manual-capture Connect destination charges. Reservation authorizes a hold; return captures only the minutes used with the commission as an application fee; overtime past the hold becomes its own off-session intent, because an authorization can't be captured beyond what it reserved. Every Stripe call carries a reservation-derived idempotency key, and webhooks claim Stripe's event ID on a primary key before any handler runs.
  • Money and the clock are deliberately decoupled — the return PIN closes the rental in the database whether or not Stripe is reachable, and capture is a retriable follow-up.
  • A hostile-client regression suite. Sixteen attacks — reading a stranger's address, inventing a price, rewriting a rental's totals, reading the counterparty's PIN, double booking — asserted to be refused, exiting non-zero on regression. It caught three real bugs during development, including a policy scoped to updated_at that silently re-opened access to a stranger's home address on any later row touch.
