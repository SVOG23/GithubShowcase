Vouchlist

Live · iOS & Android ALPHABYTE

Local recommendations that come from people you actually know.

vouchlist.app↗ Private repository

Vouchlist replaces the anonymous five-star review with a vouch from someone in your circle. You find a plumber, a restaurant or a trip because a real person you're connected to stood behind it. Three domains — Home Services, Food & Drinks, Travel — each with its own capture flow and detail schema, all sharing one social graph. I designed, built and shipped it end to end, through Apple and Google review.

The app asks for What decides
  • A pro's listingRow-level security + circle membership
  • Your phone contactsSalted SHA-256 hashes — never a readable book
  • Entry to a circleServer-issued invite code, 7-day expiry
  • An edge functionverify_jwt, declared in config
  • Privacy-preserving friend discovery. Contacts match on salted SHA-256 phone hashes, so the graph resolves the moment a hash matches a profile without the server ever holding a readable phone book.
  • Phone-OTP auth via Twilio Verify over Supabase Auth, with a five-step onboarding gate whose routing decision is a pure, unit-tested selector rather than a tangle of effects.
  • ~20 Postgres tables, RLS on every one — circles, memberships, invites, contact graph, per-domain detail tables, block lists.
  • 26 screens on 10 React Context providers + TanStack Query, each a [Provider, useHook] tuple with optimistic writes and explicit invalidation.
  • An auditable trust boundary. Every edge function's verify_jwt is declared in config, so the public/private split shows up in a diff; the public weekly-digest job is bounded by an atomic once-per-6-days gate and reads no request input.
  • Shipped through CI. EAS Build and EAS Submit to both stores, with Sentry and PostHog wired into the release build.

ModelMarketplace

iStartup Lab Micro-Grant ALPHABYTE

A two-sided marketplace for trained ML models — buy it, or win it at auction.

Private repository

Practitioners list trained models; buyers acquire them outright or win them at auction. Underneath the product it's an exercise in building real payments on Stripe with server-side guarantees — multi-flow checkout, webhook reconciliation, and business rules that live in Postgres. The University of Washington awarded it a micro-grant for market viability and architectural rigor.

The client asks for What decides
  • A new listingenforce_listing_limit — 3 / 25 / unlimited
  • A re-listenforce_relist_cooldown — 1 hour, re-checks quota
  • A completed purchasefinalize_model_purchase, keyed on the session id
  • A payoutA connected Stripe account, required at insert
  • One webhook, three flows. Purchase, auction settlement and tier subscription all land in a single handler and dispatch on a transaction_type tag — set on both the Checkout Session and subscription_data, because subscription lifecycle events only ever see the latter.
  • Atomic, idempotent fulfillment. Transaction insert, model claim, ownership transfer, ledger append and seller stats commit together inside one Postgres function keyed on a unique session id — so Stripe retries heal partial failures and duplicate events can't double-fulfill.
  • Anti-abuse in the database, not the UI. Triggers enforce per-tier quotas and the re-list cooldown; a unique partial index blocks duplicate active titles. The API translates the resulting error codes into human messages.
  • Re-listing flips ownership instead of duplicating rows, keeping downloads, reviews and history attached to one model identity across resales — which needed an RLS policy permitting the write from the current seller or the current owner.
  • No hardcoded Price IDs. One-time and auction charges build price_data inline; subscriptions reuse a Price per (tier, interval, amount) via a lookup_key, so abandoned checkouts don't litter the account.
  • Three Supabase clients, chosen deliberately — browser, cookie-aware SSR, and service-role for webhooks — kept in separate files, because mixing them silently breaks either auth or RLS.

unrot

Open source · MIT npm

A linter for the config files that steer your AI coding agents.

github.com/unrot-dev/unrot↗ npm i -D unrot↗

Agent configs rot. The repo moves on — files get renamed, scripts get replaced, conventions change — while CLAUDE.md, AGENTS.md and .cursorrules quietly keep describing a codebase that no longer exists. Nothing checks them. unrot does: static analysis plus git history, no network calls, no telemetry, no LLM calls, and it never modifies your files. npx unrot check works at the root of any repo with zero config.

The config claims What decides
  • “See docs/setup.md”The file tree — and a “did you mean…” if it moved
  • “Run npm run build”package.json — is that script real?
  • “This is how the repo works”git history — 90 days idle, 100 commits on
  • “Follow every rule here”Line count — models drop rules past ~200
  • Seven rules with teeth — broken references with rename recovery, oversized instruction files, cross-file contradictions, staleness weighed against commit volume, eager @-imports, personal paths in committed configs, and repos with no agent config at all.
  • Deliberately forgiving heuristics. Broken-refs excuses monorepo-relative paths, build artifacts, gitignored-but-present files, placeholders, package specifiers and hedged “if it exists” phrasing — so every reported error is worth fixing.
  • Measured, not asserted. On a 20-repo held-out corpus spanning Java, PHP, C#, Ruby, Go, C++ and Swift — ecosystems the rules were never tuned on — 15 of 16 error-level findings held up by hand. A mutation harness puts recall at 354/356 injected defects, with 440/440 negative controls staying quiet.
  • Found real rot in the wild across 69 open-source repos: dead source references in VS Code's Copilot config, a nonexistent path in OpenAI's Codex AGENTS.md, and a committed instruction pointing at one maintainer's laptop.
  • Fleet mode scans a whole GitHub org concurrently and grades each repo A–D in one health report. Strictly read-only — it never opens PRs.
  • Built to be a CI gate — versioned JSON schema, meaningful exit codes, and a copy-paste GitHub Actions job.

Clipr.AI

In development Computer vision

Scan your hair, preview the cut, get the spec, then cut it yourself.

Private repository

Six stages — scan, understand, preview, specify, cut, verify. You capture your hair from five guided angles, an AI analysis describes your current cut, you pick a target and preview it on yourself, then get a precise Barber Card and a step-by-step Cut Coach. Rescan afterwards and the app compares the real result against the target. The long game is a consented dataset mapping current hair → target spec → actual result.

The app asks for What decides
  • Someone's scan photosRLS + per-user folders in a private bucket
  • A hair analysisThe inference service — the mock fails closed
  • A preview renderA provider chosen by env, never a silent fallback
  • A haircutHaircutSpec v1, shared by all four surfaces
  • One spec as the source of truth. HaircutSpec v1 is a versioned schema shared by preview generation, the Barber Card, the Cut Coach and any future model — so the four surfaces can't drift into describing different haircuts.
  • Every AI capability sits behind a provider interface — segmentation, pose, analysis, preview — each with a working mock. Real providers (a vision LLM, FLUX.2, MediaPipe) activate purely through environment variables.
  • Mocks that fail closed. Hair analysis refuses to emit a canned result, and once a real inference URL is set nothing falls back to a mock — a dead service fails loudly instead of quietly serving fiction.
  • Photos of your face are treated as such. The client holds only an anon key, storage is private with per-user folder policies, RLS covers every table, and captures are downscaled on-device before upload.
  • Security tested as data. An RLS suite driven through PostgREST, a full end-to-end data-journey test, and a SQL suite run inside the database with ON_ERROR_STOP so a missing privilege fails the run instead of skipping it.
  • Honest scope. The docs ship a limitations table — no AR measurement, per-view rather than joint multi-view generation — because overstating what a model does is how demos become liabilities.

Kivo

MVP complete Marketplace

Peer-to-peer sports equipment rental, billed by the minute.

Private repository

Find gear near you on a map, rent it by the hour, verify pickup with a code, play, verify the return, and pay for the minutes you actually used. One account both rents and lends. What makes it a marketplace rather than a form is that none of the money is decided on the phone — the client is trusted with a listing id and a time window, and nothing else.

The client sends What decides
  • A pricequote_reservation(), read from the listing
  • A rental startpicked_up_at, stamped when the PIN verifies
  • An amount to chargeRecomputed in SQL at return, then captured
  • A commissionplatform_fee_bps, in a schema the client can't reach
  • A pickup addressOwner, or a renter with a live booking
  • A free time slotEXCLUDE USING gist — overlap is impossible
  • Double booking is a constraint, not a code path. A GiST exclusion constraint over listing and time range makes two overlapping live bookings impossible whatever the app does.
  • A two-sided PIN handshake. The lender shows a pickup PIN the renter enters; the renter shows a return PIN the lender enters — neither party can move the clock alone. The PINs sit in a table with RLS on, zero policies and zero grants, unreachable through the API under any role; the only way in is a function that checks who's asking and enforces attempt limits and lockout.
  • Home addresses stay hidden. Exact locations live in their own table visible only to the owner and a renter with a live booking; the public listing carries a deterministically jittered point (120–250 m, seeded from the listing id) so it can't be averaged away by polling.
  • Manual-capture Connect destination charges. Reserving authorizes a hold; returning captures only the minutes used with commission as an application fee; overtime becomes its own off-session intent, because an authorization can't be captured beyond what it reserved. Every Stripe call carries a reservation-derived idempotency key, and webhooks claim the event id on a primary key before any handler runs.
  • Money and the clock are decoupled on purpose. The return PIN closes the rental whether or not Stripe is reachable; capture is a retriable follow-up.
  • A hostile-client regression suite. Sixteen attacks — reading a stranger's address, inventing a price, rewriting totals, reading the counterparty's PIN, double booking — asserted to be refused, exiting non-zero on regression. It caught three real bugs, including a policy scoped to updated_at that silently re-opened access to a stranger's home address on any later row touch.
